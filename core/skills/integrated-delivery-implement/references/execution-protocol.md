# Integrated delivery implementation protocol

## Operational block payloads

The canonical markers are defined in the shared EXECUTION.md contract. Each block contains exactly one JSON object with a `schema` of the form `delivery-<type>/v1`, and unknown keys are rejected. Field names, types, and enums are defined only in `../../_shared/integrated-delivery/SCHEMAS.md` (section 6). Each block carries:

- `DELIVERY:PROGRESS`: `cadence`, `current_stage`, `completed`/`total` counts, `approval_identity`, and `authorization` evidence.
- `DELIVERY:CHECKPOINT`: `run_id`, `updated_utc`, `active_step`, `last_completed`, ordered `next_eligible` IDs, top-level `branch` and `head`, optional per-repository `repositories`, and `input_identity`.
- `DELIVERY:APPROVAL`: `state`, `identity` (exact plan identity), `input_identity`, `review_state`, optional `review_identity`, `blocking_findings`, `unresolved_decisions`, `operator_choice`, and `approved_utc`.
- `DELIVERY:STEP:<id>`: `id`, `status`, `run_id`, `started_utc`, `ended_utc`, `acceptance_evidence`, `evidence_refs`, `validation_results`, and `blocker` if any.

Before writing state, verify there is exactly one progress, checkpoint and approval block and one block for every declared step. Reject unknown, duplicate, nested, missing or unbalanced markers. Two layers report rejections. The library error codes are listed in `../../_shared/integrated-delivery/SCHEMAS.md` (section 2). Script reasons wrap them: `Resolve-DeliveryExecution` returns `allowed=false` with reason `grammar_invalid` (its `errors` array carries the library codes) or `legacy_marker` (library code `legacy_step_marker`); `Set-DeliveryExecutionBlock` refuses with `invalid_payload` (new text fails library validation) or `identity_changed` (normative identity would change). `approval_identity_stale` is unchanged. Replace only the intended operational block; preserve normative bytes and re-read the full plan after the write. Never edit approved normative content as part of a state update.

## Identity and eligibility

Use the shared document identity projection: normalized approved content plus the ordered set of declared input tuples (id, portable path or revision, recomputed hash, role, affected IDs). Operational blocks are excluded; all other material bytes and declared sources count. Any stale or unverifiable tuple blocks the affected step and its dependents.

Resolve-DeliveryExecution.ps1 is a read-only final eligibility check. It verifies current approval/review fields, plan projection identity, caller-recomputed input identity, cadence authorization, dependency graph, checkpoint branch/HEAD on resume, and orphaned IN_PROGRESS state. It invokes `Test-DeliveryReviewRecord.ps1` with `-ReviewRecordPath` at every selection/resume, then compares the verified review/material-input identities against APPROVAL and the caller input identity. Pass `-AliasCatalogPath` when the record uses aliases. The cadence authorization is checked against the PROGRESS `authorization` record: a missing record denies with `authorization_record_missing`, a kind different from the switch with `authorization_kind_mismatch`, a plan identity that is not the current one (case-sensitive) with `authorization_identity_mismatch`, and a step outside the granted `step_ids` with `authorization_scope_excludes_step`. Plan-dependency reasons (`plan_dependency_missing`, `plan_dependency_invalid`, `plan_dependency_identity_changed`, `plan_dependency_not_approved`, `plan_dependency_step_incomplete`, `plan_dependency_evidence_missing`, `plan_dependency_validation_missing`) deny the same way, with the predecessor path in `dependency`. A denial is a hard stop. When a plan-dependency reason appears, the executor stops and reports it and never edits the predecessor or the declaration itself. Before every selection/resume, run `Test-DeliveryPlanPreflight.ps1 -ExpectedIdentity <approved identity> -ReviewRecordPath <record>`; a blocked preflight blocks execution. The skill must obtain observed branch/HEAD and freshly recomputed input identity; the helper does not authenticate the host or the operator.

A step can run only when it is PENDING, all declared predecessors are COMPLETED, required decisions are resolved, the approval and review still match, the selected cadence authorization is current, and no human gate is open. Follow the step blocks' declared order.

## Per-step gate and recovery

One run executes one step at a time. Before invoking implementation, persist the run and active-step checkpoint and mark the step IN_PROGRESS. After implementation, inspect the actual diff and required acceptance/validation evidence; then mark COMPLETED or BLOCKED, clear active_step, and persist the checkpoint. Reread state before the next step.

An interrupted `IN_PROGRESS` step is never replayed automatically. For a Git worktree, after the resolver identifies a candidate and before setting its STEP to `IN_PROGRESS`, capture a bounded baseline with `scripts/runtime/Invoke-DeliveryGitBaseline.ps1 -Action capture -RepoPath <repo-root> -PlanPath <unit-plan> -BaselinePath <unit>/evidence/<step-id>--working-tree-baseline.json`. The evidence directory must be Git-ignored. The helper refuses overwrite and writes metadata and SHA-256 digests only; it never stores source file contents. Record the returned path and hash in that candidate step's `evidence_refs` and CHECKPOINT `baseline_evidence` (`<step-id>/<name>`); the setter verifies the reference and file hash before allowing `IN_PROGRESS`. On an orphaned step, run `-Action compare` with the same repository, plan, and baseline paths; present each changed path, status, kind, size, and hash for operator reconciliation. A changed file's prior bytes cannot be reconstructed from a digest, so inspect the current Git diff and ask the operator how to proceed. The helper covers staged and unstaged changes, untracked files, and deleted/renamed paths; Git-ignored files, clean paths, repository metadata, and the unit PLAN are outside its boundary. Capture separate declared evidence for ignored paths targeted by the plan. For a unit outside Git, use the declared directory evidence procedure in the skill; do not invoke this Git helper or invent Git branch/HEAD values. Any helper error, missing/changed/ambiguous baseline evidence, unsupported path (including a submodule or reparse point), bounds overflow, or unstable snapshot blocks execution and requires operator reconciliation. Never create a replacement baseline automatically, reset the branch, or replay an interrupted step. Branch/HEAD mismatch blocks without reset. The executor never runs Git to satisfy a plan precondition. A completed step is never selected again; an incomplete dependency cannot be skipped.

Step-by-step authorization covers one next step and ends with that step. Before the resolver switch is passed, the operator's choice is written to PROGRESS `authorization` (`kind`, `plan_identity` from the approved identity, `step_ids` as granted). A changed plan identity invalidates the recorded authorization, and a new one is required after approval of the amended content. Continuous authorization is recorded once against the exact approved plan identity and covers eligible implementation steps in that plan only. Re-check identity, dependency, gate, and checkpoint after each step. Stop on blocker, material change, stale approval, scope expansion, or Git/publication action; obtain separate authorization for such action classes.

## Evidence and baseline

- (a) When a step produces declared evidence, write it with `scripts/runtime/Invoke-DeliveryEvidence.ps1 -Action write`. Record the returned path and sha256 in that step's `DELIVERY:STEP` block `evidence_refs` through `scripts/ledger/Set-DeliveryExecutionBlock.ps1`. A step that needs the evidence is eligible only after the producer's reference exists and verifies.
- (b) Unit outside Git: before the first step, write the baseline evidence with `Invoke-DeliveryEvidence.ps1` under the first step id and its declared name, and record it in that STEP block's `evidence_refs` (status stays `PENDING`). Then write the CHECKPOINT with `location_kind` `directory`, empty `branch` and `head` strings, and `baseline_evidence` `<step-id>/<name>`. Never invent a branch or HEAD. The resolver verifies the baseline on every selection and resume instead of comparing branch and HEAD.
- (c) A missing, changed, or invalid evidence reference denies with the resolver reason (`evidence_missing`, `evidence_changed`, `evidence_ref_invalid`, `baseline_missing`, `baseline_changed`, `baseline_ref_invalid`). A failed evidence check blocks the step that needs it (step-level); a failed baseline check denies every selection (the baseline is a unit-level precondition). A helper block (for example `evidence_ambiguous`) stops the write. Do not replay or regenerate evidence automatically; ask the operator.
- (d) Limits: evidence files live under `features/NNN-slug/<UNIT>/evidence/`, outside Git when that tree is ignored. Cross-machine resume stays unsupported. A matching hash proves integrity, not authorship.

## Context and reporting

The active child receives the approved plan, repository instructions, named material inputs, dependencies, affected paths, acceptance conditions, validation commands, and reversal notes for its step. Do not forward the whole feature transcript or unrelated artifacts. The coordinator's receipt records step ID, run ID, files changed, acceptance evidence, validations and limitations. Report elapsed time only from recorded start/end timestamps.
