# Enforcement model

This page explains which layer is authoritative when the toolkit is installed in a host.

## Policy, host behavior, and hooks

`core/policy/` is the source of truth for portable behavior. An adapter publishes those files to the host-native instruction surface; it does not turn them into host permissions or replace the host's own safety UI.

Host permission prompts are generated by the host when an operation needs approval. They are not toolkit hooks, and accepting a host prompt is not the same as answering a toolkit confirmation gate. Toolkit gates remain in force even when a host auto-approves an operation.

Context hooks are optional helpers. They may record state, surface a checkpoint, or provide context; if they are unavailable, the portable policy path remains authoritative.

Security guard hooks are a distinct boundary. Four adapters publish a `PreToolUse` shim: Grok, OpenHands, ZCode, and Antigravity. Each shim denies (fail-closed) empty, malformed, or schema-invalid input. Its path and secret verdict comes from the shared `GuardCommon.ps1` compatibility helper, which always allows, so the shim does not deny on path or secret checks. The host still applies its own permission model to every request.

The following adapters register no `PreToolUse` guard: Claude, Cursor, Codex, Copilot, Hermes, and OpenCode. Claude's enforcement is the host permission model: `permissions.allow` and `permissions.ask` written by the settings merge, plus the host sandbox. Codex registers only `SubagentStop` -> `emit-trace.ps1`, and Copilot publishes no active hook. Hermes registers no hook, and the OpenCode marker plugin installs no interception hook.

The shared `GuardCommon.ps1` helper is a compatibility shim that always allows (see [guard-rules.md](../adapters/_shared/guard-rules.md)). Neither class of hook selects a model, grants permission, replaces a policy rule, or depends on private host transcripts. See [HOOKS.md](HOOKS.md).

### Behavior change: Codex and Copilot guard removal

Codex and Copilot previously registered a `PreToolUse` guard shim that denied empty, malformed, or schema-invalid input and events without a PreToolUse identity. Removing that registration is a behavior change, not a no-op: those malformed or identity-less events are no longer denied by a toolkit hook on these two adapters. The host permission model and the operator's trust settings are the only gates for them. Neither adapter publishes the guard files any more. Uninstall removes the legacy copies left by earlier installs. The change is recorded here because this repository has no CHANGELOG.

The shared path helpers resolve existing ancestors before evaluating containment, but the current shims do not use them for allow/deny (see above). Any hook that does perform a path check still cannot stop the host operation from running after the hook returns. Unless the host provides an atomic open/execute-under-root primitive, a time-of-check/time-of-use (TOCTOU) race remains a residual limitation; the hook does not claim to eliminate that race.

## Host instruction placement

Adapters preserve the host's layout. Cursor uses its rules surface; Claude, Codex, and Grok use their published rules/instruction surfaces; Antigravity embeds relevant policy in its plugin guardrails; OpenCode and ZCode use the router/host-native path described by their adapters.

GitHub Copilot has two explicit modes:

- `user`: personal instructions and skills under the user's Copilot directories.
- `repo`: repository instructions under `.github/`, including repository instructions and skills.

Do not put Copilot repository instructions in the user tree, or user instructions in a consumer repository. The adapter's mode is the placement contract.

## Always-on policy semantics

- Auto-Clarity temporarily suspends Caveman compression for security warnings, irreversible confirmations, ordered multi-step instructions, ambiguity, and requests to clarify. It restores the selected compression level afterward.
- `qa_checklist` is an in-parent checklist role. It is not a spawnable specialist, does not receive a Task, and does not create a specialist folder. Its checklist evidence belongs with the story/continuity record.

## Language resolution

Language is resolved by surface, not by a global hard-coded locale:

1. User-facing chat follows the user's active chat language.
2. Spawn prompts and specialist receipts are English.
3. Product documentation follows its selected documentation language.
4. SDD artifact prose resolves invocation override, then `preferences.json` `artifact_language`, then the manifest value, then the chat language. `null` means no override.
5. Identifiers, paths, tests, and commit messages stay English; comments and narrative source documentation mirror the touched area unless the user specifies otherwise.

Shipped locale policy files are install defaults, not a command to force that locale onto every surface.
