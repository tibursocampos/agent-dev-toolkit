# Enforcement model

This page explains which layer is authoritative when the toolkit is installed in a host.

## Policy, host behavior, and hooks

`core/policy/` is the source of truth for portable behavior. An adapter publishes those files to the host-native instruction surface; it does not turn them into host permissions or replace the host's own safety UI.

Host permission prompts are generated by the host when an operation needs approval. They are not toolkit hooks, and accepting a host prompt is not the same as answering a toolkit confirmation gate. Toolkit gates remain in force even when a host auto-approves an operation.

Context hooks are optional helpers. They may record state, surface a checkpoint, or provide context; if they are unavailable, the portable policy path remains authoritative. Security guard hooks attached to `preToolUse` are a distinct boundary: for a malformed event or a guarded write/edit, delete, patch, or shell request, they fail closed and deny the operation. Neither class of hook selects a model, grants permission, replaces a policy rule, or depends on private host transcripts. See [HOOKS.md](HOOKS.md).

Path checks resolve existing ancestors before evaluating containment, but the host operation still occurs after the hook returns. Unless the host provides an atomic open/execute-under-root primitive, a time-of-check/time-of-use (TOCTOU) race remains a residual limitation; the hook does not claim to eliminate that race.

## Host instruction placement

Adapters preserve the host's layout. Cursor uses its rules surface; Claude, Codex, and Grok use their published rules/instruction surfaces; Antigravity embeds relevant policy in its plugin guardrails; OpenCode and ZCode use the router/host-native path described by their adapters.

GitHub Copilot has two explicit modes:

- `user`: personal instructions and skills under the user's Copilot directories.
- `repo`: repository instructions under `.github/`, including repository instructions and skills.

Do not put Copilot repository instructions in the user tree, or user instructions in a consumer repository. The adapter's mode is the placement contract.

## Always-on policy semantics

- Auto-Clarity temporarily suspends Caveman compression for security warnings, irreversible confirmations, ordered multi-step instructions, ambiguity, and requests to clarify. It restores the selected compression level afterward.
- Model-cost awareness is informational only. On the first turn, when the host exposes a reliable model/capacity signal and the task is simple, it may show one cost notice. It never blocks work, maintains no vendor model allowlist, and does not repeat the notice in the same session.
- `qa_checklist` is an in-parent checklist role. It is not a spawnable specialist, does not receive a Task, and does not create a specialist folder. Its checklist evidence belongs with the story/continuity record.

## Language resolution

Language is resolved by surface, not by a global hard-coded locale:

1. User-facing chat follows the user's active chat language.
2. Spawn prompts and specialist receipts are English.
3. Product documentation follows its selected documentation language.
4. SDD artifact prose resolves invocation override, then `preferences.json` `artifact_language`, then the manifest value, then the chat language. `null` means no override.
5. Identifiers, paths, tests, and commit messages stay English; comments and narrative source documentation mirror the touched area unless the user specifies otherwise.

Shipped locale policy files are install defaults, not a command to force that locale onto every surface.
